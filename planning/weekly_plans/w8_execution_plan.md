### 00:15–00:45 | 개념: REST API·요청/응답 사이클

- **학습 목표**: HTTP 요청이 서버에 도달해 모델 예측 결과로 돌아오기까지의 흐름(요청 → 파싱 → 추론 → 응답 직렬화)을 설명할 수 있다.
- **핵심 개념**:
  - **엔드포인트**: URL 경로 + HTTP 메서드(GET/POST)의 조합. 왜 예측은 보통 POST인가? (입력 데이터를 body에 담아 보내야 하므로)
  - **Pydantic 모델**: 요청 body의 타입과 형태를 미리 정의해 자동으로 검증하는 것. 왜 수동으로 `if` 검증을 안 하고 이걸 쓰는가?
  - **동기 vs 비동기 엔드포인트**: `def` vs `async def`. 지금은 동기로 시작해도 되지만, 왜 나중에 비동기가 필요해지는지(B③·B⑥에서 다시 다룸) 미리 감만 잡기.
- **막히면**: "FastAPI 공식 튜토리얼" (fastapi.tiangolo.com) 첫 페이지만 읽기. 개념이 안 잡히면 영상 검색 "FastAPI in 15 minutes" → 그래도 안 되면 30분 넘기지 말고 다음으로.

### 00:45–01:30 | 구현: `/predict` 엔드포인트

- **학습 목표**: 저장된 sklearn 모델을 로드해 실제 입력에 대한 예측을 HTTP 응답으로 반환하는 최소 서버를 스스로 완성한다.
- **구현 과제 (스스로 작성)**:
  ```python
  # week08/main.py
  # 요구사항:
  # - FastAPI 앱 인스턴스를 만든다.
  # - Pydantic BaseModel로 입력 스키마를 정의한다.
  #   (W3 모델의 피처 개수·타입에 맞게 필드를 정한다. 예: 4개 피처면 4개 float 필드)
  # - joblib 또는 pickle로 저장해둔 W3 모델을 앱 시작 시 한 번만 로드한다(요청마다 로드 금지 — 왜 금지인지 확인 질문에서 다룸).
  # - POST /predict 엔드포인트: 입력을 받아 모델 예측 결과(클래스 + 확률)를 JSON으로 반환한다.
  # - GET /health 엔드포인트: 서버가 살아있는지 확인하는 용도로 {"status": "ok"} 반환.

  from fastapi import FastAPI
  from pydantic import BaseModel

  app = FastAPI()

  class PredictRequest(BaseModel):
      ...

  @app.post("/predict")
  def predict(request: PredictRequest):
      ...

  @app.get("/health")
  def health():
      ...
  ```
  실행: `uvicorn main:app --reload` 후 `http://127.0.0.1:8000/docs`에서 Swagger UI로 직접 테스트.
- **확인 질문**:
  - 모델을 `/predict` 함수 안에서 매번 로드하면 무엇이 느려지는가? (힌트: 디스크 I/O 비용)
  - Pydantic이 타입이 안 맞는 입력을 어떻게 거부하는지, 직접 잘못된 타입을 보내보고 에러 메시지를 확인했는가?
  - `/docs`에서 자동 생성된 API 문서는 어디서 온 정보인가? (힌트: 타입 힌트·Pydantic 스키마)

**막히면**: `uvicorn`이 실행 안 되면 포트 충돌(8000번 사용 중) 확인 → `--port 8001`로 변경. 모델 로드 에러는 저장 경로(상대/절대경로)부터 `print(os.getcwd())`로 확인.

## Day 2 (화요일) — Docker 컨테이너화 [1.5시간]

### 00:00–00:15 | 설치 확인 (보일러플레이트)

```bash
docker --version
# 설치 안 되어 있으면: Docker Desktop 설치 후 재시작
```

### 00:15–00:45 | 개념: 이미지 vs 컨테이너, 레이어

- **학습 목표**: "내 컴퓨터에서는 되는데" 문제가 왜 생기고, Docker가 그것을 어떻게 해결하는지 설명할 수 있다.
- **핵심 개념**:
  - **이미지 vs 컨테이너**: 이미지는 실행 가능한 템플릿(클래스), 컨테이너는 그 템플릿의 실행 인스턴스(객체)에 비유할 수 있음.
  - **레이어 캐싱**: `Dockerfile`의 각 명령어가 레이어를 만들고, 위에서부터 변경되지 않은 레이어는 재사용됨. 그래서 `requirements.txt` 설치를 코드 복사보다 먼저 하는 관례가 왜 빌드 속도에 유리한지.
  - **포트 매핑**: 컨테이너 내부 포트와 호스트 포트가 왜 분리되어 있고, `-p` 옵션이 그 둘을 어떻게 연결하는지.
- **막히면**: "Docker layer caching best practice" 검색. 개념이 추상적으로 느껴지면 영상 검색 "Docker explained in 100 seconds" → 그래도 안 되면 30분 넘기지 말고 실습으로 넘어가서 몸으로 익히기.

### 00:45–01:30 | 구현: Dockerfile 작성 + 빌드 + 실행

- **학습 목표**: Day 1의 FastAPI 앱을 Docker 이미지로 빌드하고, 로컬 Python 환경 없이 컨테이너만으로 실행할 수 있다.
- **구현 과제 (스스로 작성)**:
  ```dockerfile
  # week08/Dockerfile
  # 요구사항:
  # - 가벼운 python 베이스 이미지 사용 (예: python:3.11-slim)
  # - 작업 디렉토리 설정
  # - requirements.txt를 먼저 복사하고 설치 (레이어 캐싱을 위해 — 왜 이 순서인지 위 핵심개념과 연결해서 이해)
  # - 나머지 앱 코드 복사
  # - uvicorn으로 main:app을 0.0.0.0의 8000번 포트에서 실행하는 CMD 작성
  # - EXPOSE로 포트 명시
  ```
  ```bash
  # week08/requirements.txt 에 fastapi, uvicorn, scikit-learn, joblib 등 필요한 패키지 버전 명시

  # 빌드 & 실행
  docker build -t w8-model-api .
  docker run -p 8000:8000 w8-model-api
  # 다른 터미널에서 확인
  curl http://127.0.0.1:8000/health
  ```
- **확인 질문**:
  - `requirements.txt`를 코드 복사보다 먼저 COPY하면, 코드만 수정했을 때 재빌드 시간이 왜 짧아지는가?
  - 컨테이너 내부에서 `0.0.0.0`으로 바인딩해야 하는 이유는? (`127.0.0.1`로 하면 무엇이 안 되는가?)
  - `docker run`에 `-p 8000:8000` 대신 `-p 9000:8000`을 쓰면 호스트에서 어느 포트로 접속해야 하는가?

**막히면**: 빌드 실패는 에러 메시지의 마지막 줄부터 읽기(대부분 requirements 버전 충돌 아니면 COPY 경로 오타). 컨테이너는 뜨는데 접속이 안 되면 포트 매핑(`-p`)과 Dockerfile의 `CMD` 바인딩 주소(`0.0.0.0` 여부)부터 확인.

```bash
git add week08/Dockerfile week08/requirements.txt
git commit -m "W8 Day2: Docker 컨테이너화"
```

## Day 3 (수요일) — Big-O 재활성화 [1.5시간]

### 00:00–00:45 | 개념: 시간복잡도 표기법 (CLRS 핵심)

- **학습 목표**: O, Ω, Θ의 차이와, 알고리즘의 "최악의 경우"를 왜 기본값으로 보는지 설명할 수 있다.
- **핵심 개념**:
  - **O(빅오)**: 상한. "최악의 경우 이 이상 걸리지 않는다."
  - **Ω(빅오메가)**: 하한. "최선의 경우에도 이만큼은 걸린다."
  - **Θ(세타)**: 상한과 하한이 같을 때. 알고리즘의 "정확한" 성장률.
  - 왜 실무에서 대부분 O만 이야기하는가? (최악의 경우를 보장하는 것이 안전하므로)
  - 시간복잡도와 공간복잡도는 별개의 축이라는 것 (시간을 줄이려고 메모리를 더 쓰는 트레이드오프, 예: 해시맵)
- **막히면**: CLRS(Introduction to Algorithms) 3장 목차만 훑고 정의 부분 재확인. 감이 안 잡히면 영상 검색 "Big O notation explained simply" → 30분 넘으면 실습으로 넘어가기.

### 00:45–01:30 | 분석 과제: 내 코드의 시간복잡도 스스로 분석

- **학습 목표**: 지금까지 직접 짠 코드(W1 `SimplePCA`, W7 `numerical_gradient`·SGD 루프 등)를 보고, 각 부분의 시간복잡도를 직접 표기할 수 있다.
- **분석 과제 (스스로 수행, 코드 작성 아님)**:
  - W1의 `SimplePCA.fit()`에서 공분산 행렬 계산(`X.T @ X`)과 고유값 분해(`np.linalg.eigh`)는 각각 입력 크기(n=샘플 수, d=피처 수)에 대해 대략 어떤 복잡도인가? (정확한 상수는 몰라도 되고, n과 d에 대한 의존성만 판단)
  - W7의 미니배치 SGD 루프에서, 배치 크기를 바꾸면 "한 epoch당" 반복 횟수와 "한 번의 반복" 비용이 각각 어떻게 변하는가?
  - Day 1의 `/predict` 엔드포인트에서, 요청 1건을 처리하는 시간복잡도는 입력 피처 개수에 비례하는가, 상수인가?
  - 아래 함수를 직접 종이 또는 마크다운에 시간복잡도와 함께 정리해보세요 (구현하지 않아도 됨, 분석만):
    ```
    함수 시그니처만 제시 — 구현하지 말고 시간복잡도만 판단할 것:
    def has_duplicate(nums: list[int]) -> bool: ...
    → 이중 for문으로 짜면? / set을 쓰면? 각각 시간·공간복잡도는?
    ```
- **확인 질문**:
  - "공간을 더 써서 시간을 줄인다"는 트레이드오프를 위 `has_duplicate` 예시로 설명할 수 있는가?
  - 행렬 곱 `X.T @ X`의 시간복잡도가 왜 데이터 크기가 커질수록 병목이 되는지, W1에서 다룬 행렬 곱의 정의와 연결해 설명할 수 있는가?

**막히면**: 특정 numpy 연산의 복잡도가 궁금하면 "numpy matrix multiplication time complexity" 검색. 30분 넘게 막히면 정확한 값 대신 "n에 비례한다" 수준의 대략적 판단만 적어두고 다음으로.

## Day 4 (목요일) — LeetCode + ⭐영어 루틴 시작 [1.5시간]

### 00:00–00:45 | 알고리즘 (Big-O 적용 연습)

```
- [ ] Climbing Stairs (Easy)
- [ ] Merge Intervals (Medium)
```

- **학습 목표**: 위 두 문제를 풀고, 각각의 시간·공간복잡도를 스스로 판단해 주석으로 남긴다.
- **구현 과제 (스스로 작성)**:
  - `Climbing Stairs`: 함수 시그니처만 — `def climb_stairs(n: int) -> int: ...` DP(동적계획법) 또는 재귀+메모이제이션 중 하나를 선택해 구현. 왜 순수 재귀는 지수시간이 되는지 확인질문에서 다룸.
  - `Merge Intervals`: 함수 시그니처만 — `def merge(intervals: list[list[int]]) -> list[list[int]]: ...` 정렬을 먼저 해야 하는 이유를 생각하며 구현.
- **확인 질문**:
  - `Climbing Stairs`를 메모이제이션 없이 순수 재귀로 풀면 왜 시간복잡도가 O(2^n)이 되는가? 메모이제이션을 추가하면 왜 O(n)으로 줄어드는가?
  - `Merge Intervals`에서 정렬(O(n log n))이 전체 알고리즘의 시간복잡도를 어떻게 지배하는가?

**막히면**: "climbing stairs dynamic programming intuition" 또는 "merge intervals sorting approach" 검색 → 여전히 안 풀리면 문제 설명(에디토리얼)의 접근 방식만 읽고 코드는 직접 짜기. 30분 넘으면 다음으로.
